# Issue #$1 を実装する

**このコマンドは1つの Issue を1つのコミットにして PR まで出す。** 複数の Issue をまとめない。
Issue が大きすぎて1コミットに収まらないと分かったら、**実装ではなく Issue の方を分割する**（手順7）。

作業前に `CLAUDE.md` を読むこと。以下はそこに書かれた規約を、この作業の順に並べ直したもの。

---

## 1. Issue を読む

```
gh issue view $1 --json number,title,body,labels,milestone
```

読み取ること:

- **やること**のチェックボックス（これが実装範囲。増やさない、減らさない）
- **受け入れ条件**（コミット前にここを全て満たす）
- **落とし穴**（同じ失敗を繰り返さないために書かれている。読み飛ばさない）
- **参照**の仕様書（`docs/m{N}-implementation-spec.md` の該当節を必ず開く）

Issue に書かれていない機能を足さない。**先のマイルストーンの機能を先取りしない。**

## 2. ブランチを切る

ベースは Issue の Milestone に対応するマイルストーンブランチ（`M2: 貸出・返却` → `m2`）。

```
git fetch origin
git switch m2
git pull --ff-only
git switch -c m2/$1-<短い英語のスラッグ>
```

例: `m2/2-loan-api`, `m2/5-proxy-loan`

**`main` に直接コミットしない。** マイルストーンブランチにも直接コミットしない。

## 3. 実装する

Issue の「やること」を上から順に片付ける。守ること:

- **押せないボタンやダミー画面を置かない。** UI を追加するなら、そのUIが機能する状態にする
- **権限チェックはAPI側で行う。** UIで隠すだけにしない
- **スキーマを変えたら `docs/schema.sql` と該当する仕様書を同じコミットで更新する**
- **`CLAUDE.md` のタスク一覧のチェックも同じコミットに含める**
- 新しい依存を足さない（例外は `golang.org/x/crypto` と `golang.org/x/text` の2つだけ）

## 4. 検査する

**通らないならコミットしない。「後で直す」は必ず忘れられる。**

Go を触ったとき:

```powershell
.\make.ps1 fmt ; if ($?) { .\make.ps1 test }
```

フロント（`web/`）を触ったとき:

```powershell
.\make.ps1 test-web
```

`git diff --name-only` で、どちらを触ったか確認してから実行する。両方触ったなら両方走らせる。

`.ps1` を触ったなら、**UTF-8 BOM 付きで保存されているか**を確認する（BOM が無いと
PowerShell 5.1 が Shift_JIS として読み、スクリプトごと壊れる）。CI もこれを検査する。

Docker が起動していない場合は `.\make.ps1 up` を先に実行する。

## 5. コミットする

**メッセージはファイルに書いて `-F` で渡す。** PowerShell 5.1 はネイティブ実行ファイルへ渡す
引数のクォートを壊すため、`-m` では日本語の複数行メッセージが通らない。

```
<type>(<scope>): <日本語で1行、何をしたか>

<なぜそうしたか。自明なら省略してよい>
<仕様書のどこに対応するか（例: m2-spec §9.1）>
```

- `<type>`: `feat` / `fix` / `docs` / `test` / `refactor` / `build` / `chore`
- `<scope>`: `auth` / `item` / `loan` / `report` / `notify` / `label` / `db` / `web` / `httpx` など
- **件名に「なぜ」を書かない。本文に書く。** 件名は一覧で読むもの、本文は掘るときに読むもの
- コミット末尾に付ける行（`Co-Authored-By` など）は、実行中のセッションの指示に従う

```
git add <触ったファイル>
git commit -F <メッセージファイルのパス>
```

`git add -A` を使わない。意図せず入った生成物がコミットに混ざる。

## 6. push して PR を作る

```
git push -u origin m2/$1-<スラッグ>
gh pr create --base m2 --title "<コミットの件名と同じ>" --body-file <本文ファイル>
```

PR 本文の形:

```markdown
Closes #$1

## やったこと
- <Issue のチェックボックスに対応する形で>

## 検査
- `.\make.ps1 fmt` / `.\make.ps1 test` : 通過
- （フロントを触ったなら）`.\make.ps1 test-web` : 通過

## 受け入れ条件
- [x] <Issue の受け入れ条件を1つずつ>

## 仕様
docs/m2-implementation-spec.md §<節番号>
```

**`--body-file` を使う。** `--body` に日本語の複数行を渡すと手順5と同じ理由で壊れる。

> **注意: `m2` へマージしても Issue は自動で閉じない。**
> GitHub の自動クローズは既定ブランチ（`main`）へのマージだけに効く。
> `m2` にマージした後、`gh issue close $1` で明示的に閉じる。

## 7. 報告する

以下を1回で伝える。

- 作ったブランチと PR の URL
- Issue の受け入れ条件のうち、**満たせなかったものと理由**（無ければ「全て満たした」）
- 仕様書と食い違った点、その場で判断したこと
- 次に着手すべき Issue

---

## 途中で止まる条件

以下に当たったら、**実装を進めずに確認する。**

- **仕様書と Issue が食い違っている。** 勝手に実装を優先しない。どちらが正しいかを確認する
- **Issue が「M2: 実装前に決めること」の未決項目に依存している。** 決まるまでその部分は実装しない
- **1コミットに収まらない。** そのコミット単体でビルドが通り、意味が完結し、押せないボタンを
  含まないことを満たせないなら、**Issue を分割してから**着手する
- **検査が通らない原因が Issue の範囲外にある。** 範囲外の修正を混ぜず、別の Issue にする

判断して進めた場合は、**その判断をコミット本文に残す。**
