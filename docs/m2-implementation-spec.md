# M2 実装依頼書：貸出・返却

## 0. 前提

M1（認証・備品マスタ・QR発行）が完了していること。
**M2 の完了条件は「QRを読んでから3タップ以内で借用が完了すること」。** 機能が揃っていても、この操作量を超えたら M2 は未完了とみなす。

このドキュメントは M1 の依頼書と同じ粒度で読むこと。**「なぜそうするか」を含めて書いてある部分は、実装の都合で変えない。** 変えたくなったら先に確認する。

---

## 1. スコープ

### 実装する
- 借用登録（QRから、代理登録、事後登録）
- 借用の取り消し（誤登録の訂正）
- 返却登録
- 破損報告（任意ボタン）
- 貸出中一覧（全員に公開）
- 自分の貸出中・履歴

### 実装しない（M3以降）
定期通知、期限超過通知、所在不明報告、棚卸しモード、返却期限の延長。
ただし**代理登録の本人通知メールだけは M2 に含める**（SMTP 基盤も M2 の先頭で作る。実装済み）。

SMTP は**未設定でも動く**。学内SMTPの可否が未確定なため、メールを前提にすると
使えなかった時点でシステム全体が止まる。認証はメールに依存しない設計（M1）を保ち、
メールは「送れる人にだけ送る」補助手段として扱う。

### 実装しない（恒久的にスコープ外）
予約機能、購入・会計管理（`equipment-management-requirements.md §1`）。

## 2. 既存システムの調査（設計の裏取り）

貸出管理は枯れた領域で、先行実装が多い。**同じ落とし穴を踏み直さないために調べた。**
以下は「採ったもの」と「採らなかったもの、およびその理由」。**採らなかった理由の方が重要で、
後から「なぜ無いのか」を訊かれたときの答えになる。**

### Snipe-IT（OSS の資産管理。checkout / checkin モデル）

| 見たもの | 本システムでどうするか |
|---|---|
| 貸出可能な状態（deployable）でない資産は貸せない | **採る。** 廃棄・自由利用品を API 側で拒否する（§9） |
| 既に貸出中の資産は再度貸せない | **採る。** ただしアプリの検査ではなく DB の部分ユニークインデックスで拒否する（§8） |
| `expected_checkin_date`（返却予定日）は任意項目 | **採る。ただし既定値を入れる。** 空欄のまま貸し出せる設計は、期限超過の検知（M3）が働かない行を作る |
| 貸出・返却の変更前後を監査ログに残す | **形を変えて採る。** `loans` の行そのものが監査ログ。**削除も上書きもしない** |
| 貸出先が「ユーザー / 場所 / 別の資産」の3種類 | **採らない。** サークルでは人にしか貸さない。多態にした分だけ画面と API の分岐が増える |
| 返却時に状態ラベルを選ばせる | **採らない。** 返却に入力を足すと摩擦になる。状態の更新は破損報告に寄せる（§7） |
| カスタムフィールド | **採らない。** 数年で担当者が入れ替わる前提では、定義できる自由度そのものが負債になる |

### 国内の備品管理サービス（備品管理クラウド、カシカン ほか）

| 見たもの | 本システムでどうするか |
|---|---|
| 貸出台帳の項目は「貸出日 / 返却予定日 / 貸出者 / 型番 / 状態・損傷の有無」 | **概ね採る。** 状態は借用**前**に見せる（§3）。損傷は破損報告で持つ |
| 「使用目的」欄 | **採らない。** 必須にすれば摩擦、任意にすれば書かれない。どちらに転んでも記録が増えない |
| QRを読んで貸出・返却 | **採る。** ただし**アプリ内カメラを作らない。** OS標準カメラで URL に飛ぶだけにする（`url-design.md §1`） |
| 返却期限のリマインド | **採る。ただし M3。** M2 では通知を作らない |
| 貸出予約・期間指定予約 | **採らない。** 要件定義でスコープ外。予約は「借りていないのに押さえる」状態を作り、所在の把握という目的から遠ざかる |
| 返却期限の延長 | **M2 では作らない。** 期限超過通知（M3）が無い段階で延長だけ作っても、延長する動機が発生しない。M3 で通知と合わせて再検討する |
| 一括返却 | **採らない（当面）。** `/loans/mine` の各行から返せれば足りる。数十点を同時に返す運用が実際に出てから作る |
| 貸出履歴の CSV 出力 | **M1 で実装済み**（備品マスタ）。貸出履歴の出力は必要になってから足す |

### 二重送信（idempotency）の扱い

一般的な解は Idempotency-Key ヘッダだが、**本システムには要らない。**
「同一備品の未返却の貸出は1行しか存在できない」という制約（§8）が、そのまま冪等性の保証になる。
借用ボタンを2度押しても、2回目は 409 で弾かれる。**キーを持ち回る仕組みを足すより、
DB の制約1行の方が壊れにくい。**

- [Asset Checkout & Checkin — Snipe-IT](https://deepwiki.com/grokability/snipe-it/2.5-asset-checkout-and-checkin)
- [貸出管理の効率化を徹底解説（アストロラボ）](https://www.astrolab.co.jp/bihinkanri/column/loan-management-efficiency/)
- [スマホでかんたん貸出管理カシカン](https://casican.blogspot.com/)
- [物品管理システム18選比較（デジタル化の窓口）](https://digi-mado.jp/category/business/office-equipment-management-system/)

## 3. 借用フロー（最重要）

### 操作の想定
1. QRをOS標準カメラで読む → `/i/0042` に遷移（**ここまで操作ゼロ**）
2. 画面に「借りる」ボタン → タップ（1）
3. 内容を確認して「この内容で借りる」 → タップ（2）

**2タップで完了する形にする。** 3タップは上限であって目標ではない。代理登録・事後登録・
返却予定日の変更は、この経路の**外側**（確認画面の「変更する」）に置き、既定のまま進む人の
タップ数を増やさない。

**返却予定日は借用日+14日を最初から入れておき、変更したい人だけ変える。** 日付入力を必須にしない。ここが摩擦の最大の発生源になる。

### 備品詳細画面（`/i/{code}`）の表示分岐

| 備品の状態 | 表示 |
|---|---|
| 貸出可能 | 「借りる」ボタン（主要導線として大きく） |
| 貸出中（他人） | 借用者名・返却予定日・「破損を報告」 |
| 貸出中（自分） | 「返す」ボタン・「破損を報告」 |
| 自由利用品 | 情報表示のみ。**貸出ボタンを出さない** |
| `condition = 廃棄` | 貸出不可を明示 |
| `location_status = 所在不明_*` | 「借りる」は出すが警告を表示（下記） |

### 必須：借用画面に現在の状態と備考を表示する

「状態：良好 / 備考：脚のロックが緩い」を借りる前に見せる。

破損報告は任意ボタンなので、**報告されないまま次の人が借りるケースが必ず出る。** そのとき現状表示がないと、前の人の破損が次の人の責任になる。次に借りる人が食い違いに気づけば、その場で報告できる。実装は軽く、責任の誤帰属を防ぐ効果は大きい。

### 所在不明の備品が見つかった場合の自動処理

`location_status` が `所在不明_未確認` / `所在不明_確定` の備品に対して借用が成立したら、
**`location_status` を `在庫` に戻す**（借用と同一トランザクション）。

**見つかったという事実は、借りた人が報告するのではなく、借用操作から自動で導く。** 追加操作を求めない。

> **M2 での制限：** `missing_reports` テーブルは M3 で作る（M2 では存在しない）。
> したがって「該当する報告を `発見済み` に更新する」処理は **M3 側で、この自動復帰に足す。**
> M2 の受け入れ条件は `location_status` が戻るところまでとする（§13）。

## 4. 代理登録

「〇〇さんが持っていくのを見た」を第三者が登録できる。

- 借用画面で借用者を自分以外から選択できる（既定は自分。**選択は確認画面の「変更する」の中に置く**）
- `loans.user_id` = 借用者、`loans.registered_by` = 登録者
- **借用者本人にメール通知する**（「あなたの名前で借用が登録されました」＋訂正リンク）
- 本人が訂正できる導線を必ず設ける（§5）

これは「本人が記録しなくても穴が埋まる」ための仕組み。記録漏れ対策の中核なので、導線を深い階層に埋めないこと。

### メール
- 宛先: 借用者の `users.email`。**未設定なら送らない**（`notify.ErrNoRecipient` を `errors.Is` で拾って進む）
- 件名: `[備品] あなたの名前で借用が登録されました`
- 本文: 備品コード・品名・登録者名・借用日時・返却予定日・訂正先URL（`{HOST_URL}/loans/mine`）
- **送信の失敗で借用を巻き戻さない。** ログに残して 201 を返す。
  通知が送れなかったことを理由に記録を消すと、最も避けたい「記録が無い」状態に戻る
- 自分で自分の借用を登録した場合は送らない

---

## 5. 借用の取り消し（訂正）

代理登録には誤登録がつきまとう。**「これは自分じゃない」を本人がその場で直せること**が
代理登録を成立させる条件になる。

- `loans` の行は**削除しない。** `cancelled_at` / `cancelled_by` / `cancel_reason` を立てる
- **「返却済み」と「そもそも借りていない」は別の事実。** 取り消しを返却として記録すると、
  借りていない人の返却履歴が残り、破損の追跡時に誤った経路をたどることになる
- 取り消せるのは**未返却の貸出だけ。** 返却済みの履歴は消せない
- 実行できるのは**借用者本人・登録者・admin** の3者
- 取り消した備品は再度借用できる（部分ユニークインデックスは取り消し済みを除外する）

## 6. 返却

- `/i/{code}` の「返す」ボタン、または `/loans/mine` の各行から
- **借用者本人以外も返却登録できる。** 棚に戻っているのを見つけた人が処理できないと、記録が永久にズレたままになる。`loans.returned_by` に実行者を記録する
- 返却時に確認ダイアログを出さない（摩擦低減。誤返却は再度借りれば済む）
- 返却時に状態を訊かない。破損があれば「破損を報告」を押す（§7）

### 設計上の非対称性
**借用の記録漏れは致命的（誰が持っているか永久に不明）、返却の記録漏れは自己修復する（本人に聞けば解決）。** UIの作り込みは借用側に厚く、返却側は薄くてよい。

---

## 7. 破損報告

- 「破損を報告」ボタンを備品詳細に常設（貸出中・在庫中どちらでも押せる）
- 入力：破損箇所の説明（必須）、写真（任意。§13 で可否を決める）
- `damage_reports` に記録。貸出中に報告された場合は `loan_id` を紐付ける
- **報告と同時に `items.condition` を `要修理` に変更する。** 承認を待たない（所在不明報告と同じ思想）
- 運営は `/admin/damages` で追認し、`確認済み` / `修理済み` / `廃棄` に更新する

### 追認と `items.condition` の連動

| `damage_reports.status` | `items.condition` |
|---|---|
| `未確認`（報告直後） | `要修理` に変更する |
| `確認済み` | 変えない（`要修理` のまま） |
| `修理済み` | `良好` に戻す |
| `廃棄` | `廃棄` にする |

**既に `廃棄` の備品は報告を受けても `要修理` に戻さない。** 廃棄は終端状態で、
報告によって復活すると、廃棄済みのはずのものが一覧に現れる。

## 8. データモデル（`0002_loans.sql`）

**M2 で使う分だけ作る。** `missing_reports` / `inventory_checks` / `api_tokens` は
それぞれ M3・M4 で足す。完成形の設計は `equipment-management-requirements.md §5`。

```sql
CREATE TABLE loans (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id       INTEGER NOT NULL REFERENCES items(id),
    -- 借用者。代理登録では registered_by と異なる
    user_id       INTEGER NOT NULL REFERENCES users(id),
    -- 登録者。本人が登録した場合も自分の id を入れる。
    -- NULL可にして「NULLなら本人」とすると、代理かどうかの判定が2通りになる
    registered_by INTEGER NOT NULL REFERENCES users(id),
    borrowed_at   TEXT    NOT NULL DEFAULT (datetime('now')),   -- UTC
    due_date      TEXT    NOT NULL,                             -- 'YYYY-MM-DD'（JST）
    returned_at   TEXT,                                         -- NULL = 貸出中（UTC）
    -- 返却を実行した人。借用者とは限らない
    returned_by   INTEGER REFERENCES users(id),
    -- 誤登録の取り消し。返却とは別の事実として持つ（§5）
    cancelled_at  TEXT,
    cancelled_by  INTEGER REFERENCES users(id),
    cancel_reason TEXT    NOT NULL DEFAULT '',
    note          TEXT    NOT NULL DEFAULT '',
    created_at    TEXT    NOT NULL DEFAULT (datetime('now')),
    updated_at    TEXT    NOT NULL DEFAULT (datetime('now'))
);

-- 二重貸出をDBで拒否する。アプリ側の検査（SELECT してから INSERT）は競合に負ける。
-- 取り消し済みは対象外。取り消した備品は再度借りられる
CREATE UNIQUE INDEX idx_loans_active_item
    ON loans(item_id) WHERE returned_at IS NULL AND cancelled_at IS NULL;

CREATE INDEX idx_loans_user ON loans(user_id, borrowed_at DESC);
CREATE INDEX idx_loans_item ON loans(item_id, borrowed_at DESC);

CREATE TABLE damage_reports (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id      INTEGER NOT NULL REFERENCES items(id),
    -- 貸出中に報告されたら紐付ける。在庫中の報告では NULL
    loan_id      INTEGER REFERENCES loans(id),
    reporter_id  INTEGER NOT NULL REFERENCES users(id),
    reported_at  TEXT    NOT NULL DEFAULT (datetime('now')),
    description  TEXT    NOT NULL,
    photo_path   TEXT,
    status       TEXT    NOT NULL DEFAULT '未確認'
                         CHECK (status IN ('未確認', '確認済み', '修理済み', '廃棄')),
    confirmed_by INTEGER REFERENCES users(id),
    confirmed_at TEXT,
    note         TEXT    NOT NULL DEFAULT '',
    created_at   TEXT    NOT NULL DEFAULT (datetime('now')),
    updated_at   TEXT    NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_damage_reports_item   ON damage_reports(item_id, reported_at DESC);
CREATE INDEX idx_damage_reports_status ON damage_reports(status);
```

**`items` に貸出中フラグを足さない。** 貸出状態は `loans` から導出する
（`returned_at IS NULL AND cancelled_at IS NULL`）。二重管理は必ず不整合を起こす。

`docs/schema.sql` を同じコミットで更新すること。

### 時刻とタイムゾーン（実装前に読むこと）

- 保存は **UTC**。M1 と同じく `datetime('now')` が返す `YYYY-MM-DD HH:MM:SS` 形式のテキスト
- `due_date` は **JST の日付**。`YYYY-MM-DD` で持つ。時刻を持たせない
- **既定の返却予定日 = 借用日時を JST に直した日付 + 14日。** UTC の日付で計算すると、
  JST の 00:00〜09:00 に借りた分が1日ずれる
- 期限超過の判定も JST の日付で行う（`due_date < 今日(JST)`）
- **`time.LoadLocation("Asia/Tokyo")` を使わない。** 本番イメージは scratch で
  tzdata が入っておらず、実行時に失敗する。`time.FixedZone("JST", 9*60*60)` を
  1箇所に定義して使い回す（`time/tzdata` を埋め込む手もあるが、
  日本以外で使う予定がないため定数の方が安い）
- **API のレスポンスに載せる時刻は RFC3339（`+09:00`）に揃える。**
  `2026-09-10T19:30:00+09:00`。フロントで `new Date()` に渡せる形にする

## 9. API仕様

共通:
- 認証はすべて必須（`requireLogin`）。admin 限定のものは明記する
- エラー本文は M1 と同じ `{"error": "...", "code": "..."}`（`httpx.WriteErrorCode`）
- **`code` は文言ではなく識別子。** フロントは `code` で分岐する

### 9.1 借用

```
POST /api/items/{code}/loans
```

```json
{
  "user_id": 12,
  "due_date": "2026-09-24",
  "borrowed_at": "2026-09-08T19:30:00+09:00",
  "note": ""
}
```

| 項目 | 必須 | 既定 | 備考 |
|---|---|---|---|
| `user_id` | | 自分 | 代理登録のときだけ指定する |
| `due_date` | | 借用日(JST)+14日 | |
| `borrowed_at` | | 現在時刻 | 事後登録のときだけ指定する。**未来は不可** |
| `note` | | `""` | |

**すべて省略可能にする。** 空の JSON（`{}`）で自分の借用が成立することが、
3タップの前提になる。

成功: `201` で `{"loan": {...}, "item": {...}}`。
**更新後の item も返す。** 所在不明から在庫へ戻った結果を、画面が再取得せずに反映できる。

| 状況 | status | `code` | 文言 |
|---|---|---|---|
| 備品が無い | 404 | | 備品が見つからない |
| 自由利用品 | 400 | `free_use` | 自由利用品は借用の記録が要らない |
| `condition = 廃棄` | 400 | `discarded` | 廃棄済みの備品は借りられない |
| 既に貸出中 | 409 | `already_borrowed` | 他の人が先に借りました |
| `user_id` が無効・退会済み | 400 | `invalid_user` | その利用者は選べない |
| `due_date` < 借用日 | 400 | `invalid_due_date` | 返却予定日が借用日より前 |
| `borrowed_at` が未来 | 400 | `future_borrowed_at` | 借用日時に未来は指定できない |

**409 を 500 にしない。** 部分ユニークインデックスの違反を捕まえて 409 に変換する。
競合は異常ではなく、2人が同時に同じ三脚を借りようとしただけ。

### 9.2 返却

```
POST /api/items/{code}/return
```

本文なし（`{}` も可）。**借用者以外も実行できる。**

成功: `200` で `{"loan": {...}, "item": {...}}`。`returned_by` に実行者を記録する。

| 状況 | status | `code` |
|---|---|---|
| 備品が無い | 404 | |
| 貸出中でない | 409 | `not_borrowed` |

**貸出中でない場合を 200 で黙って成功にしない。** 二重タップは 409 を受けて
画面を再取得すればよく、「返した気になっているが記録が無い」より遥かに良い。

### 9.3 取り消し

```
POST /api/loans/{id}/cancel
```

```json
{ "reason": "自分は借りていない" }
```

実行できるのは**借用者本人・登録者・admin**。対象は**未返却の貸出だけ。**

| 状況 | status | `code` |
|---|---|---|
| 貸出が無い | 404 | |
| 権限が無い | 403 | |
| 返却済み | 409 | `already_returned` |
| 取り消し済み | 409 | `already_cancelled` |

### 9.4 破損報告

```
POST /api/items/{code}/damages     -- 全員
GET  /api/damages?status=未確認     -- admin のみ
POST /api/damages/{id}/status      -- admin のみ
```

- 報告本文: `{"description": "脚のロックが割れている"}`（必須）
- 報告と同時に `items.condition = '要修理'`（既に `廃棄` なら変えない）。同一トランザクション
- 貸出中なら `loan_id` を紐付ける
- 状態更新: `{"status": "修理済み", "note": ""}` → §7 の表に従って `items.condition` を連動させる

状態遷移を `PUT /api/damages/{id}` にせず個別経路にしているのは、M1 の
`POST /api/items/{code}/discard` と同じ形に揃えるため。**追認は「全項目を送り直す更新」ではなく、
1つの状態遷移**として扱う。

### 9.5 一覧

```
GET /api/loans?overdue=1&user_id=12&q=三脚
GET /api/loans/mine
```

- `GET /api/loans`: 未返却の貸出のみ。**全メンバーが見られる。**
  備品コード・品名・借用者名・借用日・返却予定日・超過日数を返す
- `GET /api/loans/mine`: `{"active": [...], "returned": [...]}` を1リクエストで返す。
  `returned` は新しい順に既定50件（`limit` で変更可）
- **取り消し済みはどちらにも出さない**（履歴としては残るが、一覧に出すと誤登録が
  「起きた事実」として全員に見え続ける）

### 9.6 備品詳細への追加（M1 の経路を拡張する）

```
GET /api/items/{code}
```

レスポンスに `loan` を足す。貸出中でなければ `null`。

```json
{
  "...M1の項目": "...",
  "loan": {
    "id": 3,
    "user": { "id": 12, "name": "山田" },
    "borrowed_at": "2026-09-10T19:30:00+09:00",
    "due_date": "2026-09-24",
    "overdue_days": 0
  }
}
```

**「借りられるか」を API が判定して返さない。** `is_free_use` / `condition` / `loan` から
画面が組み立てる。判定をサーバに持たせると、同じ判断が API と画面の2箇所に散る。

### 9.7 貸出のレスポンス形

```json
{
  "id": 3,
  "item": { "code": "0042", "name": "三脚（大）" },
  "user": { "id": 12, "name": "山田" },
  "registered_by": { "id": 8, "name": "佐藤" },
  "is_proxy": true,
  "borrowed_at": "2026-09-10T19:30:00+09:00",
  "due_date": "2026-09-24",
  "returned_at": null,
  "returned_by": null,
  "overdue_days": 0,
  "note": ""
}
```

`is_proxy` はサーバで計算して返す（`user_id != registered_by`）。
画面が2つの id を比べる形にすると、比べ忘れた画面ができる。

## 10. 画面

| URL | 内容 | ログイン |
|---|---|---|
| `/i/{code}` | 備品詳細。状態に応じた分岐（§3）と「借りる」「返す」「破損を報告」 | 必須 |
| `/i/{code}/borrow` | 借用の確認画面。代理・事後登録・返却予定日の変更もここ | 必須 |
| `/loans` | 貸出中一覧（全員分） | 必須 |
| `/loans/mine` | 自分の貸出中・履歴。各行から返却・取り消し | 必須 |
| `/admin/damages` | 破損報告の追認 | admin |

- **`/i/{code}` の経路は変えない**（ラベルは貼り替えられない）
- 未ログインで QR を読んだ場合の復帰は M1 の `next` の仕組みに乗る。**新しく作らない**
- トップ（`/`）に「自分が借りているもの」と「貸出中一覧」への導線を置く。
  事後登録の導線もここから1タップで届く位置に置く（§4 の目的）
- 一覧の絞り込みは URL のクエリに持つ（M1 の `/items` と同じ）
- **期限超過を視覚的に区別する。** ただし良好・在庫のような「正常」の目印は出さない。
  全行に付く印は、注意すべき行を埋もれさせる

## 12. 受け入れ条件

- [ ] QRを読んでから借用完了まで**3タップ以内**（実機・実スマホで計測する）
- [ ] 返却予定日が最初から入力されており、触らずに借用できる
- [ ] 空の JSON（`{}`）で自分の借用が成立する
- [ ] 未ログイン状態でQRを読み、認証後に元の備品ページへ戻って借用できる
- [ ] 代理登録すると、借用者本人にメールが届く（`SMTP_HOST` 未設定なら送らずに成功する）
- [ ] 代理登録された本人が `/loans/mine` から取り消せる。取り消した備品は再度借用できる
- [ ] 同一備品を2人が同時に借りようとすると、後者に 409 が返る（**500 にならない**）
- [ ] 借用者以外が返却登録でき、`returned_by` に記録される
- [ ] 所在不明の備品を借用すると、自動で `location_status` が `在庫` に戻る
- [ ] 借用画面に現在の状態と備考が表示される
- [ ] 自由利用品には借用ボタンが出ず、API も 400 で拒否する（**UIで隠すだけにしない**）
- [ ] 廃棄済みの備品は借用できない
- [ ] 破損報告と同時に `condition` が `要修理` になり、admin の追認前から一覧に反映される
- [ ] JST の 00:00〜09:00 に借用しても、返却予定日が借用日+14日になる
- [ ] `/loans` に取り消し済みの貸出が出ない
- [ ] member が `/api/damages`（追認）を叩くと 403 になる
