# サークル備品管理システム 要件定義書

## 1. 背景と目的

サークルの部室にある備品が一切管理されておらず、以下の状態にある。

- 何があって何がないかが誰にも分からない
- 部屋は学科管理だが、備品の利用については担当教員から包括的な許可を得ている（**要: メール等で文面化**）
- 管理体制がないため、備品の貸出を許可できない

本システムの目的は、**「今どこに何があり、誰が持っているか」を継続的に把握できる状態を作ること**である。

### 解決すること
- 備品の所在と貸出状況の可視化
- 破損・紛失時に「誰がいつ借りていたか」を遡れること
- マスタデータの書き込み権限を運営に限定すること

### 解決しないこと（スコープ外）
- 記録漏れをゼロにすること（物理的強制がない以上、不可能。摩擦低減と事後検知で対処する）
- 備品の購入・会計管理
- 予約機能（初期リリースでは実装しない）

### 成功の判定基準
- 学期末の棚卸しで、所在不明の備品が把握できている状態
- メンバーが貸出記録を「面倒だから飛ばす」と思わない操作量（借用完了まで3タップ以内）

---

## 2. 設計思想（実装判断の拠り所）

以下は本システムの全機能に優先する原則。実装で迷ったらここに戻る。

1. **記録する手間 < 記録しない手間**。この不等号が崩れたら、その機能は使われない。
2. **借用の記録漏れは致命的、返却の記録漏れは自己修復する**。実装リソースは借用側に厚く配分する。
3. **追跡対象を減らすことが、遵守率を上げる最短経路**。全部を守ろうとするルールは全部が守られなくなる。
4. **記録されなかった事実を、システムが「正常」として表示しない**。不確かな状態は不確かなまま表現する。
5. **可視性は罰則より強い**。誰が何を持っているかが全員に見える状態を作る。

## 3. 前提条件

| 項目 | 内容 |
|---|---|
| 利用者数 | 数十名規模 |
| 備品点数 | 初期は数百点想定（棚卸しで確定） |
| 主な利用デバイス | スマートフォン（**モバイルファーストで設計**） |
| 同時利用 | ほぼ発生しない |
| デプロイ | オンプレミス（インフラは別担当） |
| 学外アクセス | **要確認事項**（不可の場合、事後入力・通知リンクが機能しない） |

## 4. 権限モデル

| ロール | 権限 |
|---|---|
| 運営（admin） | 備品マスタの追加・編集・削除、所在不明報告の確認、ユーザー管理、棚卸し実施 |
| メンバー（member） | 貸出・返却、所在不明報告、一覧閲覧、自分の貸出状況確認 |

メンバーは**既存の備品レコードを書き換えられない**。これがスプレッドシート共有ではなくシステム化する主目的。

### 認証方式
- **admin が発行する ID + パスワード**方式を採用（マジックリンクは不採用）
- セッションは長期保持（1年程度）。初回のみログイン、以降は開けば即操作
- 初期パスワードは admin が発行し、初回ログイン時に本人が変更する
- パスワードリセットは admin による再発行のみ（自己リセット導線を作らない）
- 理由:
  - 名前選択式では「俺は借りてない」という否認を排除できず、責任追及の根拠にならない。個人ごとの認証情報を持つ本方式ならこれを満たす
  - **マジックリンクは SMTP が使えることが動作の前提**になる。学内SMTPの可否が未確定な段階でログイン手段をメールに依存させると、使えなかった時点でシステムが起動できない。パスワード方式はメールに一切依存しない
- `users.email` は**通知専用**。認証に使わないため未設定でも運用できる。SMTP が使えない場合はメール通知をスキップする
- QR読み取りは**OS標準カメラアプリ**を使用（URLに遷移するだけ）。アプリ内カメラの実装は不要（棚卸しモードのみ例外、M3）

## 5. データモデル

### users
| カラム | 型 | 備考 |
|---|---|---|
| id | PK | |
| name | text | 表示名 |
| login_id | text | ログインID（admin が発行、一意） |
| password_hash | text | bcrypt。平文は保存しない |
| must_change_password | bool | 初期パスワードのままなら 1。初回ログイン時に変更を強制 |
| email | text | **通知専用**（認証には使わない）。NULL可 |
| role | enum | admin / member |
| is_active | bool | 卒業者は無効化（履歴保持のため削除しない） |
| created_at | timestamp | |

### items（備品マスタ）
| カラム | 型 | 備考 |
|---|---|---|
| id | PK | |
| code | text | QRに埋め込む一意コード |
| name | text | |
| category | text | 本 / 機器 / 工具 など |
| is_free_use | bool | **true = 記録不要の自由利用品**。貸出フローの対象外 |
| owner | enum | サークル / 学科 |
| location | text | 保管場所 |
| condition | enum | 良好 / 要修理 / 廃棄 |
| location_status | enum | 在庫 / 所在不明（未確認） / 所在不明（確定） |
| photo_path | text | 任意 |
| note | text | |
| created_at | timestamp | |

**設計上の注意**
- 貸出中かどうかは `loans` から導出する（`returned_at IS NULL`）。items 側に持たせると二重管理になり必ず不整合を起こす
- `location_status` と貸出状態は**独立**。「貸出中かつ所在不明」は起こり得る
- 自由利用品には**物理的にQRを貼らない**（またはラベル色を変える）。DBのフラグだけではメンバーが判断できない

### loans（貸出履歴）
| カラム | 型 | 備考 |
|---|---|---|
| id | PK | |
| item_id | FK | |
| user_id | FK | 借用者 |
| borrowed_at | timestamp | |
| due_date | date | **デフォルト値（借用日+14日）を自動入力**。変更したい人だけ変える |
| returned_at | timestamp | null = 貸出中 |
| registered_by | FK | 代理登録の場合に借用者と異なる |
| note | text | |

**返却しても行を削除しない。** 破損・紛失の追跡はこの履歴が唯一の根拠になる。

### missing_reports（所在不明報告）
| カラム | 型 | 備考 |
|---|---|---|
| id | PK | |
| item_id | FK | |
| reporter_id | FK | **報告者を必ず記録**（複数人の独立報告は強い証拠になる） |
| reported_at | timestamp | |
| status | enum | 未確認 / 確定 / 発見済み |
| confirmed_by | FK | 運営による追認 |
| confirmed_at | timestamp | |
| note | text | |

**承認フローは設けない。** 報告は即時反映され `location_status` を「所在不明（未確認）」にする。運営は事後に「確定」または「発見済み」へ更新する（承認ではなく追認）。承認待ちの間、システムが「在庫あり」と嘘をつく状態を避けるため。

### inventory_checks / inventory_check_items（棚卸し）
学期2回の大掃除に合わせて実施。チェック単位で「確認済み／未発見」を記録し、未発見品は自動で所在不明（未確認）に遷移させる。

### api_tokens
サイネージ等の外部連携用。read-only スコープ。

## 6. 機能要件（マイルストーン別）

### M1: 基盤
- ユーザー認証（マジックリンク）、権限制御
- 備品マスタ CRUD（運営のみ）
- **CSV一括インポート**（初期棚卸し用）
- **管理画面からの1件ずつ登録**（スマホ対応、写真添付可）
- QRコード発行 + **一括ラベル印刷（PDF出力）**

### M2: 貸出
- QR読み取り → 借用登録（3タップ以内、返却予定日はデフォルト入力済み）
- 返却登録
- **代理登録**（「〇〇さんが持っていくのを見た」を第三者が登録。本人に通知）
- **事後登録**（持ち出し後に自宅からでも登録可能な導線）
- 貸出中一覧（全メンバーに公開）
- 自分の貸出中一覧

### M3: 検知・通知
- 所在不明報告（メンバーから即時、運営が追認）
- 月次通知（借用中の全員に「まだ持っていますか」）
- 返却予定日超過の通知
- 棚卸しモード（QRを連続スキャンして確認済みにする）

### M4: 外部連携
- 公開API（read-only、トークン認証）
  - `GET /api/v1/items` 備品一覧
  - `GET /api/v1/loans/active` 貸出中一覧
  - `GET /api/v1/items/missing` 所在不明一覧
- サイネージ連携（貸出中一覧の常時表示）

**M4は必ず最後に実装する。** データ構造が固まる前にAPIを公開すると、後から変更できなくなる。

---

## 7. 非機能要件

- **CSVエクスポートを必ず実装**。システムが死んでもデータは残る
- バックアップ手順を文書化（SQLite ならファイルコピーで完結）
- 引き継ぎ: 管理者アカウントの追加手順、ドメイン・証明書の管理者を明記
- 卒業者の扱い: アカウント無効化のみ。削除すると貸出履歴が壊れる

---

## 8. 技術スタック

| 領域 | 選定 |
|---|---|
| フロントエンド | React（モバイルファースト） |
| バックエンド | Go |
| DB | **SQLite 推奨** |
| コンテナ | Docker |
| デプロイ | オンプレミス |

### DB選定の根拠
同時書き込みがほぼ発生しない規模であり、PostgreSQL の運用コストに見合う要件がない。**バックアップがファイル1個のコピーで済む**点は、引き継ぎ先の技術力が読めないサークル運営において決定的な利点。将来の移行余地を残すため、SQL は方言に依存しない書き方にとどめる。
