# M3 実装依頼書：検知・通知・棚卸し

> **注意：この仕様は M1・M2 を実運用してから見直すこと。** 通知頻度も棚卸しの操作性も、実際の使われ方を見ないと適切な値が決まらない。現時点では規模見積もりのためのドラフトとして扱う。

## 0. 位置づけ

M1・M2 が「記録する仕組み」なら、M3 は**記録漏れを前提として、ズレを炙り出す仕組み**。

物理的強制（施錠棚）を採用しない以上、記録漏れをゼロにする方法は存在しない。M3 の役割は予防ではなく**検知と事後回収**である。この前提を実装者と共有すること。

---

## 1. スコープ

- 所在不明報告（メンバー即時、運営が追認）
- 定期通知（月次・期限超過）
- 棚卸しモード（連続スキャン）

---

## 2. 所在不明報告

### フロー
1. メンバーが備品詳細から「所在不明を報告」
2. **即時に `items.location_status` を `所在不明_未確認` に変更**し、`missing_reports` を作成
3. 運営が `/admin/missing` で追認し、`確定` / `発見済み` に更新

### 承認フローを設けない理由
承認を挟むと、運営が処理するまでシステムは「棚にある」と表示し続ける。**記録が正しいという嘘を、システムが権威をもって主張する状態**が生まれる。これは紙の台帳より悪い。

3段階ステータス（`未確認` / `確定` / `発見済み`）を持たせることで、「事実は即座に反映しつつ、確定情報ではないことも表現する」を両立させる。承認ではなく**追認**。

### 報告者を必ず記録する
`missing_reports.reporter_id`。同じ備品に複数人が独立して報告した場合、**それ自体が承認者1人より強い証拠になる。** 詳細画面には報告件数と報告者を表示すること。

### 貸出中の備品が報告された場合
借用者にメールで通知する。本人が持っているだけの可能性が高く、聞けば解決する。

---

## 3. 定期通知

### 種別

| 種別 | タイミング | 内容 |
|---|---|---|
| 月次 | 毎月1日 09:00 JST | 貸出中の全備品を1通にまとめて送る |
| 期限超過 | 返却予定日の翌日 09:00 JST | 超過した備品を1通にまとめて送る |
| 代理登録 | 即時（M2で実装済み） | 本人への確認 |

### 集約する（1人1通）

**借用者ごとに1通に集約し、備品ごとの個別送信はしない。**

5点借りている人に5通届く設計は、高確率で「まとめて無視」されるようになり、通知そのものの効力が失われる。**通知は打てば効く資源ではなく、打ちすぎると効かなくなる資源。**

個別送信の利点（何を返すべきか明確、メールから直接返却できる）は、**集約メールの各行に返却リンクを置けば同様に実現できる。** 失われるメリットはない。

### メール本文の要件
- 各備品の行に、ワンタップで返却できるリンクを置く（`/i/{code}/return`）
- リンクはログイン済みセッションで開ける想定。未ログインならマジックリンク経由で復帰
- 「返却済みなら無視してよい」と明記しない。**無視を許容すると通知が死ぬ**

### 期限超過を毎日送らない
超過翌日に1通送ったら、以降は月次に含めるだけにする。毎日の督促は数日で無視されるようになり、その後は何を送っても届かなくなる。

### 冪等性
アプリ内スケジューラは、再起動やダウンタイムで実行タイミングを取りこぼす。

**`notification_log` の `(user_id, kind, dedupe_key)` ユニーク制約で判定する。** 起動時と定期実行時の両方で「未送信分があれば送る」ロジックにすること。時刻トリガーだけに依存しない。

- 月次の `dedupe_key`: `'2026-09'`
- 期限超過の `dedupe_key`: `'loan:123'`

## 4. 棚卸しモード

### 運用
学期2回、サークルの大掃除に合わせて実施する。**新しい行事を作らない**ことが継続の条件。

### フロー
1. 運営が `/admin/inventory` で棚卸しを開始（`inventory_checks` を作成）
2. **QRを連続スキャンする。** 1点読むごとに画面に留まり、次をすぐ読める状態にする
3. 進捗を表示（確認済み ○件 / 全 ○件）
4. 終了時、その回に確認されなかった備品を**一括で `所在不明_未確認` に遷移**させる

### 連続スキャンのUI
ここだけは OS 標準カメラでは足りない。**ブラウザ内カメラ（`getUserMedia` + QRデコード）で、読むたびに画面遷移しない実装が必要。**

数百点を1点ずつページ遷移させると、棚卸しが物理的に終わらない。M3 で最も実装コストが高い箇所なので、見積もりに注意すること。

### 未発見の扱い
一括遷移の前に、**未確認の備品一覧をプレビューする。** 単純に確認し忘れただけのものが混ざるため、除外できるようにする。

---

## 5. 受け入れ条件

- [ ] 所在不明報告が即時に反映され、承認を待たない
- [ ] 同じ備品への複数報告が、報告者付きで一覧できる
- [ ] 貸出中の備品が報告されると、借用者に通知が届く
- [ ] 月次通知が借用者ごとに1通に集約され、各行に返却リンクがある
- [ ] サーバを通知時刻をまたいで停止・再起動しても、通知が1通だけ送られる
- [ ] 同じ通知が二度送られない
- [ ] 棚卸しモードで、QRを連続して読める（1点ごとに画面遷移しない）
- [ ] 棚卸し終了時、未確認品の一覧をプレビューしてから一括遷移できる

---

## 6. 見直し予定の項目

M1・M2 の運用後に、以下を実データで再検討する。

- 月次という頻度が適切か（返却率を見て判断）
- 返却予定日のデフォルト14日が適切か
- 棚卸し年2回で発覚の遅れが許容範囲か（四半期に変える余地）
- 所在不明報告が実際に使われているか（使われていないなら導線の問題）
